# ADR-0017: Authentication with Better Auth; JWKS service token to core

- Status: Accepted
- Date: 2026-10-09
- Deciders: Javi
- Related requirements: FR-ACC-01, FR-ACC-03, FR-ACC-04, NFR-05, NFR-06, Enterprise
- Supersedes: [ADR-0009](0009-auth-authjs-service-tokens-sso.md)

## Context

ADR-0009 chose Auth.js. We switch to Better Auth: a TypeScript-native, framework-agnostic
auth library with first-class Next.js App Router support, typed server/client APIs, a plugin
model (magic link, OAuth, JWT, organizations) and explicit control of its database schema. The
rest of ADR-0009 (sessions in Postgres, a short-lived signed token to core, SSO later) is kept.

Two things ADR-0009 left open and we resolve here: the auth library's own table named `account`
collides with our business tenant table `account`; and the web→core token was an HS256 shared
secret, which couples key material across two deployables.

## Options considered

| Option | Pros | Cons |
| --- | --- | --- |
| Better Auth in web + JWKS-signed service token to core | TS-native, typed, plugins for magic link/OAuth/JWT/orgs; org plugin maps to our account/membership; asymmetric token needs no shared secret | Newer than Auth.js; we own the DB schema mapping |
| Auth.js (ADR-0009) | Owner's prior familiarity | Adapter-driven schema, weaker typing, HS256 coupling |
| Auth in core (Spring Security) | One auth system | Duplicates session/webhook/billing logic in both apps |

## Decision

**Better Auth in `apps/web`** with the email **magic link** and **Google** social providers;
**database sessions in Postgres**. Better Auth's schema is owned by Flyway (ADR-0005), not
generated by the library: we pin table names via Better Auth config and create them in migrations.
`apps/web` reads/writes these tables through Better Auth's Postgres (Kysely) adapter over
introspected types and **never migrates** (ADR-0005).

**Table naming** (resolves the collision): business tenant table stays `account`; Better Auth
models are mapped to `app_user` (user), `auth_session` (session), `auth_identity` (its `account`
= OAuth provider link) and `auth_verification` (verification). The **organization plugin** backs
our tenant model: a Better Auth organization ↔ our `account`, membership ↔ `account_member`.

**Service token to core**: Better Auth's **JWT plugin** issues a short-lived (≤ 2 min) token with
`sub` (user), `acct` (active organization/account) and `plan`, signed with an asymmetric key
(EdDSA). Core verifies it against the web app's **JWKS endpoint** (no shared secret) and enforces
tenant isolation on every query. Enterprise SSO (SAML/OIDC) via a Better Auth SSO provider /
WorkOS-equivalent when the Enterprise plan ships.

## Consequences

- One auth library decision changes; the boundary and tenant-isolation rules are unchanged.
- Core caches the JWKS and rejects tokens that fail signature or `exp` (401), before any DB access.
- `packages/plans` is still the only source of plan limits; the token only carries the plan id.
- `apps/web` directly reads **only** its auth tables (`app_user`, `auth_*`) and any explicit read
  models; all business reads/writes go through core (keeps ADR-0003). CLAUDE.md and
  `docs/architecture.md` updated to name Better Auth.
